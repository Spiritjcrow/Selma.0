## 3. Academic explanation: why many PRs stay open

1. **Dependency graph vs. item count.** Several PRs are stacked (e.g., #95 on #78 and #94 on #89). Each carries a predecessor constraint. Running tasks in arbitrary order creates rebasing failures and duplicate integration work. Represent tasks as a directed acyclic graph (DAG), perform topological scheduling, and preserve a single canonical integration path.
2. **Evidence taxonomy.** `STATIC_OK` means parse/lint succeeded. `UNIT_OK` means isolated units executed. `INTEGRATION_OK` means real components communicated. `PACKAGE_OK` means a reproducible distributable exists. `DEVICE_OK` means it actually ran on supported hardware. `DEPLOYED_OK` means the live endpoint is verifiably accessible. `RELEASE_OK` adds security, licensing, privacy, rollback and operator sign-off. No level implies the next.
3. **Fault domains.** A GitHub Actions zero-job failure is a scheduling/admission fault, not an application test defect. Repairing source will not change a nonexecuting runner. Route external provider issues into a separate escalation queue with a verified alternative execution path.
4. **Falsifiability.** Every milestone needs a counterexample: what result would prove the fix *didn't* work? Use baseline failing test, minimal patch, reproducible green rerun, and failure-mode/rollback checks. `test succeeded` without commit SHA and output provenance is not sufficient.
5. **Observability.** A system that cannot tell `no backend`, `stale data`, `failed authentication`, `permission denied`, `CI never started`, and `test failed` apart cannot self-heal reliably. Encode typed failure classes and explicit responses.
6. **Safety in autonomy.** Multiple agents need idempotency, leases, narrowly scoped capabilities, immutable worktrees, policy-gated external effects, and independent verification. A model's generated instruction, an issue description, or a peer signature does not grant execution authority.
7. **Economic correctness.** Financial simulation must segregate test ledgers from real balances. Live micropayments, custody, trading, and automated transfers require explicit financial authorization, anti-fraud controls, reconciliation, and compliance reviews; self-healing must not invent or replay payments.

## 4. Per-item record contract

Each repair must write: `repository`, `issue/pr URL`, `created_at`, `observed_at`, `base_sha`, `failure_class`, `reproduction`, `attempted_fix`, `diff_sha256`, `tests`, `logs`, `artifact_sha256`, `device/environment`, `external dependencies`, `owner`, `review verdict`, `rollback target`, `next_action`, `resolution status`, `closure evidence`, and `redacted/private` flag. Never put credentials or personal/financial records in public GitHub comments.

**Closure policy:** close a ticket only on actual acceptance evidence or explicit human-approved supersession/duplicate closure. A commit, green fixture test, plan, or PR does not by itself close a hardware, deployment, or payment milestone.
